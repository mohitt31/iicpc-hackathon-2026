# Phase 2.3 — 3-Machine Distributed Scale Run (THE last rank-1 hardware item)

**Deliverable (the committed evidence):** `kubectl get nodes` shows **≥3 Ready nodes**,
bot pods scheduled on each, **1000+ bots** aggregate (headline target ~30k), and the
accounting holds (`Sent ≈ Acked`, backpressure surfaces as `EAGAIN`, 0 double-counts).
Output committed to `verified_runs/aftab/2.3_distributed_run.txt`.

**What this run proves / does NOT.** It proves horizontal distribution + the DaemonSet
shape + accounting under scale across real nodes. It does **NOT** report a new latency
number (per-bot latency on time-sliced nodes = OS scheduler, not the engine — see RESULTS
§17.4). The 7.7µs latency number already comes from the isolated single-box run. So the 3
nodes need only be **x86-64 Linux** — they do NOT all need isolated bare-metal.

---

## 0. Hardware reality & chosen path

Team has 2 Macs (arm64) + 1 Windows + Aftab's x86+KVM box. The bot-engine image is **amd64**,
so an arm64 Mac **cannot** be a bot node (would need a multi-arch rebuild). Macs are
**kubectl drivers only**. Chosen path:

### ▶ PLAN A (PRIMARY — what we run to win): 3 KVM VMs on Aftab's one x86 box
`infra/terraform/benchmark_pool.tf` already boots N libvirt VMs, each auto-joining k3s via
cloud-init with the benchmark label+taint. Set count=3 → a real 3-node k3s cluster on one
host. All amd64 (existing image, **zero rebuild**), no Tailscale, no cloud, no Mac/Windows
nodes. Honest label for the writeup: *"3-node k3s cluster across 3 KVM VMs on one isolated
host — distribution + scale + accounting proof"* (this is NOT a latency run; see top).

### ▷ PLAN B (fallback, only if a judge insists on separate physical boxes)
Aftab x86 (server) + Windows→WSL2 Ubuntu (amd64 agent) + 1 cheap x86 cloud VM (amd64 agent),
joined via Tailscale. See §1B. Only 1 cloud VM needed; Macs still drivers.

| Role | Plan A | Plan B |
|---|---|---|
| control plane (k3s server) | Aftab host (or VM-0) | Aftab x86 box |
| 3 agent nodes | 3 libvirt VMs (terraform) | Aftab + Windows WSL2 + 1 cloud VM |
| kubectl driver | Mohit/Manish Mac | Mohit/Manish Mac |

## 1A. PLAN A — boot the 3-node cluster (Aftab, on his x86 box)

```bash
# On Aftab's host: ensure k3s server is up and grab its URL + token
sudo cat /var/lib/rancher/k3s/server/node-token        # -> K3S_TOKEN
# K3S_URL = https://<aftab-host-LAN-ip>:6443

# Boot 3 benchmark VMs; cloud-init auto-joins k3s + applies the benchmark label/taint.
# Fill the k3s join line in benchmark_pool.tf cloud-init (URL+token above) if not already.
cd infra/terraform
terraform init
terraform apply -var bench_node_count=3 -var bench_vcpus=4 -auto-approve

# Verify all 3 VMs joined:
sudo k3s kubectl get nodes -o wide                      # expect 3 Ready, all labeled
```
Because cloud-init joins with `--node-label node-role.hft/benchmark=true`, **step 3a (labeling)
is already done** — skip it on Plan A. Proceed to §2.

## 1B. PLAN B — per-machine join (only if running Plan B)

On **each** agent (Windows WSL2 Ubuntu + the cloud VM; NOT the Mac):
```bash
curl -fsSL https://tailscale.com/install.sh | sh && sudo tailscale up   # one-time auth
curl -sfL https://get.k3s.io | \
  K3S_URL=https://<SERVER_TAILSCALE_IP>:6443 \
  K3S_TOKEN='<K3S_NODE_TOKEN>' \
  sh -s - --node-label node-role.hft/benchmark=true
```
(If the server was reinstalled, regen token: `sudo cat /var/lib/rancher/k3s/server/node-token`.)
Then do step 3a labeling in §3 for any node that didn't self-label.

## 3. ANTIGRAVITY (from the Mac, with KUBECONFIG set) — label, scale, apply

```bash
cd ~/iicpc-hackathon-2026
export KUBECONFIG=$PWD/kubeconfig-2.3.yaml

# 3a. Label ALL nodes so the bot-fleet DaemonSet (nodeSelector node-role.hft/benchmark=true) schedules
for n in $(kubectl get nodes -o name); do
  kubectl label "$n" node-role.hft/benchmark=true --overwrite
done

# 3b. Set the bot count. DaemonSet = 1 pod/node, so aggregate = bots-per-pod × nodes.
#     Edit infra/k8s/platform.yaml line "--bots=8":
#       - clears the "1000+ bots" bar:   --bots=400   (×3 ≈ 1200)
#       - headline 30k attempt:          --bots=10000 (×3 = 30000)
#     Start at 400, confirm clean accounting, THEN push to 10000.
#     (one engine pod fans in all connections; if it saturates, dial back — commit
#      whatever holds clean Sent≈Acked. Honest number > round number.)

# 3c. Apply the whole stack
kubectl apply -f infra/k8s/

# 3d. Watch it come up (engine first, then bot pods on every node)
kubectl -n hft-bench get pods -o wide -w     # Ctrl-C when all Running
```

## Troubleshooting

| Symptom | Cause → fix |
|---|---|
| Node won't join | Tailscale not up, or token rotated → `sudo tailscale status`; regenerate token (`/var/lib/rancher/k3s/server/node-token`) |
| Bot pods `Pending` | Nodes not labeled → step 3a; or taint mismatch (manifest tolerates `dedicated=benchmark:NoSchedule` only) |
| Bot `CrashLoopBackOff` | Should not — manifest already has `--no-gate` (gate can't pass in a container). Check `kubectl logs` for image arch (must be x86) |
| `reference-engine` DNS fails in bot | DaemonSet already sets `dnsPolicy: ClusterFirstWithHostNet` — confirm it survived your edit |
| Engine saturates at high `--bots` | Single engine pod, N→1 fan-in by design → lower `--bots`, commit the clean run |
| Mac kubectl can't reach cluster | kubeconfig still points at 127.0.0.1 → re-run the `sed` in step 2; confirm `tailscale status` shows the server |
